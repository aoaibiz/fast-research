# AI エージェントのための情報取得層としての RustXNG

RustXNG は「SearXNG の Rust 実装」ではありません。**ローカルで動く AI エージェントが、Web 検索と事実確認（Grounding）を自律的に行うための、セルフホスト型の高速情報取得エンジン**です。

## なぜこの位置づけなのか

AI エージェントは「検索して、読んで、判断する」を繰り返します。そのとき外側に必要なのは、次の性質を持つ層です。

| 要件 | なぜ要るか | RustXNG の対応 |
| --- | --- | --- |
| **API キーなしで動く** | エージェントを配布・量産するたびに課金と鍵管理が増える | 0 円・鍵不要 |
| **ローカルで完結する** | 社内データを扱うエージェントは外部 API に検索内容を渡せない | 自分のサーバーで完結 |
| **速い** | エージェントは 1 タスクで何十回も検索する。1 回 1 秒の差が積み上がる | 同じ検索の 2 回目は **0.01 秒**（キャッシュ） |
| **本文まで取れる** | 事実確認には「そのページに何が書いてあるか」が要る | 1 リクエストで上位 5 件の本文（約 32,000 字） |
| **壊れても止まらない** | 検索は外部サイトに依存する。1 つ落ちても答えを返す必要がある | 180 エンジン並列・自動休止・サスペンド回復 |
| **安全である** | エージェントは信頼できない URL を扱う。SSRF はそのまま社内ネットワークへの侵入になる | 下記の SSRF 対策 |

## SSRF 対策（AI 用途では必須）

エージェントが検索結果の URL を辿って本文を取りに行くとき、その URL は**第三者の検索エンジンが返したもの**です。悪意ある結果や汚染されたインデックスが `http://169.254.169.254/`（クラウドのメタデータ）や `http://127.0.0.1:8080/`（社内サービス）を指していた場合、素朴な実装はそのまま取得してしまいます。

RustXNG は**外向きの取得先を公開アドレスに限定**します。

- ループバック・プライベート・リンクローカル（`169.254.0.0/16`）・未指定アドレスを拒否
- `image_proxy` / `favicon_proxy` に加え、**`include_raw_content` のページ取得にも同じ判定**を適用
- 判定は取得の直前に行う（リダイレクト先も含めて公開アドレスのみ）

```rust
// aggregator.rs: 検索結果の URL は信頼しない
if !crate::web::image_proxy::is_public_url(url) {
    return None;
}
```

## なぜ「テスト自動化とセキュリティ監査」が不可欠なのか

このツールは**エージェントの判断材料を供給する層**です。ここが静かに壊れると、エージェントは間違った情報を根拠に行動します。しかも壊れ方は派手ではありません。

| 壊れ方 | 気づきにくい理由 | 対策 |
| --- | --- | --- |
| パーサーが静かに 0 件を返す | エラーにならず「結果なし」に見える | 797 のユニットテスト・17 の統合テスト |
| エンジンが一斉にレート制限 | 検索は成功するが精度が落ちるだけ | nightly ベンチマーク（100 問・下限割れで CI 失敗） |
| 依存クレートの脆弱性 | 動作は変わらないまま穴が開く | `cargo audit` を CI で実行（現在 既定ビルドの脆弱性 0 件） |
| SSRF の穴 | 正常な検索では表面化しない | 公開アドレス限定の判定をテストで固定 |

つまり **「動いているように見える」状態が最も危険**で、それを検出できるのは自動テストと継続的な監査だけです。

## エージェントから使う方法

```bash
# 1. 起動（既定 8888）
rustxng &

# 2. 検索 + 本文取得（Grounding 用）
curl "http://127.0.0.1:8888/search?q=...&format=json&include_raw_content=1"
```

応答には `results[]`（`title` / `url` / `content` / `raw_content`）が入ります。`raw_content` はページ本文（最大 8,000 字/件）なので、そのままモデルに渡して根拠にできます。
